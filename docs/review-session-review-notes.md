## Round 1 findings

- **[P1] New human input can disappear from the live attention queue.** `python/review_session/core.py:208-210` refreshes live comparisons for queue/status/create but not reply/edit. If source changes after the previous refresh, the human replies, and the agent next queries the queue, `refresh` at lines 151-152 marks the thread outdated and suppresses both the old question and the deliberate new reply. Reproduced through the real core with a temporary repository: change live source, append `Please inspect your new change`, query agent queue; result was `[]`, with two human revisions suppressed. The accepted contract explicitly keeps deliberate new input on outdated threads actionable. Refresh the relevant live comparison before applying human input, within the same transaction, so only already-existing revisions are suppressed. Cover reply and edit without requiring an intervening status/queue read.

- **[P1] A composition can silently attach to code selected by a concurrent writer.** `lua/review_session/init.lua:184-194` captures only path/side/line at composition time, and `python/review_session/core.py:240-248` selects whichever snapshot is current at save time. Reproduced with the headless editor test: open a note on `new`, change the disk line to `changed by concurrent agent` before writing the composition, then inspect its retained source; it contains the latter text. Explicit comparison refresh during composition can similarly change a committed target. This loses the original annotation context. Carry the selected comparison identity and file fingerprint into create, validate them transactionally, and reject stale saves while preserving composition text (or retain a separately captured original anchor). A revision guard is simpler than silently remapping annotations.

- **[P1] PR coordinate validation can approve the wrong old-side text.** `python/review_session/publish.py:66,80-83` checks base/head tip SHAs and numerical patch coverage, but GitHub's PR diff uses the merge base. When the target branch has advanced independently, the original old snapshot can differ from the PR's old side even though the PR API base/head equal the comparison. Reproduced with divergent commits and a mocked real-shape PR patch: original old-side line 2 was `one`, PR old-side line 2 was `two`, yet preview approved `LEFT,line=2`. This can publish a finding on unrelated code. Validate that the original old snapshot/coordinates actually match the PR diff base, or reject inline publication for an incompatible comparison. Preserve the historical anchor; do not silently remap it. Include a diverged-base fixture, rather than only wrong-SHA and out-of-hunk tests.

- **[P1] Real working-tree codediff panes fail exact-comparison matching.** `lua/review_session/codediff.lua:12-14` requires `modified_revision == "WORKING"`. The installed codediff explorer initially creates that value but changes its per-file working side to `nil`. Independently ran `/tmp/review-session-real-codediff.lua` against the actual installed plugin: the final git context contained the exact original SHA and omitted modified_revision, and `review.location()` rejected both panes after `ReviewDiff`. Current-file toggle, source comments and decorations consequently fail in the default live viewer workflow. Accept the actual working-side representation while still rejecting STAGED and mismatched base/repository identities. Add a real-plugin integration check or at least a double for the post-file-selection `nil` representation; the existing double fixes the value at WORKING and misses this transition.

## Optional improvements and limits

- Codediff update currently decorates every matching comparison tab using the active session's cache, rather than checking each tab's selected session. Two sessions of the same repo/base/head can temporarily display each other's status in hidden tabs until the newly active tab refreshes. Prefer scoping decorations to their owning context if extending multi-session UX; this was inspected, not interactively reproduced.
- Open thread Markdown views capture their messages/state and do not update when async cache refresh observes an external reply. Reopening through the picker retrieves fresh data. Automatic refresh of unmodified views would help the ongoing human/agent workflow, but is not an explicit accepted automatic-refresh requirement.
- All-tree snapshot capture and full transactional JSON rewriting are simple, but potentially expensive on large source trees; no benchmark establishes a practical performance defect. Keep the documented limitation rather than adding incremental infrastructure without measurement.
- No live GitHub publication, interactive UX, clean standalone pip install or broad platform compatibility check. The identified publication and queue issues remain material correctness risks until fixed and rechecked.

Remedy tradeoffs, without requiring a new framework:

- Since context selection is tab-local and only one tab is visible, a small active-context policy may suffice: source marking operates only for the current context; tab/context switches synchronously clear and repaint from the already-loaded cache before starting asynchronous reloads; tabs with no loaded context clear prior marks. Regression should use the actual shared pane IDs and check immediately after TabEnter, before waiting for a subprocess.
- Suppressing source marks for a buffer owned by distinct contexts is smaller than a provider and prevents incorrect annotations, but gives up source annotations in the common same-comparison/two-session case. If chosen, disclose the limitation visibly/document it; explorer statuses remain usable. It should not be described as full annotation support in those sessions.
- A window-aware ephemeral decoration provider can retain annotations per context despite shared buffers and avoids switch-time stale displays. It adds lifecycle/rendering logic, but it can remain a small local display mechanism over the existing cache. Do not add a provider framework or perform CLI work from rendering.
