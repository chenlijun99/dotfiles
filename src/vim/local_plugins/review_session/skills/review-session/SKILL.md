---
name: review-session
description: Use the review-session CLI to exchange review threads with a human, inspect original code versions, track exact reviewed file pairs and record review coverage in an explicitly selected local review workspace.
---

Use the installed `review-session` executable. If unavailable, the plugin checkout supplies `bin/review-session` (Python 3.10+); resolve this skill's symlink before locating the plugin root. Do not write the session database directly or invent another session store.

- **Select the workspace explicitly.** Require the user's session path; never infer a repository-global active session. `--session` takes a directory. If the user specifies its `session.sqlite3` file, use that file's parent. Use `--role agent` before every command. Initialize a new workspace only when requested; loading or navigating an existing one needs no comparison setup.
- **Read pending input precisely.** `review-session --session SESSION --role agent queue` returns shared threads and exact pending human message revisions. Human-only threads are filtered, not protected by filesystem secrecy. Retrieve `show --thread ID` for discussion and `source --thread ID --side old|new` for retained original text. Committed/index/worktree versions can differ from the current checkout; investigate the actual anchor rather than silently choosing current lines.
- **Respond after handling the input.** Use `reply --thread ID --ack EXACT_REVISION --body-file reply.md`, repeating `--ack` for each revision actually handled. Reading is not acknowledgement. A stale token cannot clear a newer edit, including edit-and-revert. Decide whether to discuss, investigate, challenge a finding or change code from the user's intent; do not equate a resolved discussion with completed coverage.
- **Create findings against exact source.** `create --repo REPO --old BASE --new HEAD --path FILE --side new --start N --end N --body-file finding.md` creates a shared agent thread. Omit the range for file scope, or use `--scope review` for a review-wide finding. `--new WORKTREE` and `--old INDEX` refer to saved working text and index stage 0; `INDEX:1`, `INDEX:2`, `INDEX:3` select actual conflict stages. No comparison enrollment is needed. Preserve unrelated source and unsaved human buffers.
- **Guard delayed findings.** `view` with those same target flags returns exact pair fingerprints and resolved target descriptors without writing storage. If composition/investigation spans concurrent edits, pass its returned `--expected-fingerprint TOKEN` to `create`, using the nested `files[0].view` descriptor through `--view-file FILE` (not the entire `view` response wrapper); reject stale context rather than moving a finding to different code. Separate old/new paths are available for renames. Programmatic callers may send a JSON request via `--request-file -`.
- **Keep coverage at review scope.** `coverage --target LABEL --body-file coverage.md` records target/base, intended behavior, guidance and completed/inapplicable/unverified checks once per review, rather than copying the checklist into findings. `coverage` retrieves those records. `history` identifies explicitly reviewed pairs; `mark` is a deliberate reviewed action, not a consequence of browsing or creating a finding. “Another revision reviewed” implies no ordering or partial coverage.
- **Preserve publication boundaries.** Creating shared threads or choosing a local draft is not permission to post remotely. Do not run `publish` unless explicitly authorized for the concrete destination and selected draft. Inline publication validates PR applicability; incompatible intermediate anchors require explicit human-selected reanchor or `--summary`, never silent line mapping. Receipts and original snapshots stay in the session. Deleting a session does not undo remote comments or source changes.

All successful commands emit one JSON value and exit 0; errors exit nonzero. Keep a failed or stale response body and report the failure instead of claiming the input handled. Use `--help` for command options. Thread IDs and message revision tokens are opaque; do not substitute body hashes or agent process IDs.
