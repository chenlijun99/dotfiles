# Persistent discussions with coding agents during code review

Investigated 2026-11-09 and updated 2026-11-10 through primary documentation and source, using `gh` for GitHub access. No interactive installations, usability tests, or token benchmarks were performed. Claims below distinguish existing capabilities from engineering recommendations. No exact turnkey solution covering the complete requested workflow was found among the inspected tools.

## Accepted viewer-driven session behavior

The later design interview supersedes the earlier fixed-comparison workflow. The authoritative implementation decision is [ADR 0001](../src/vim/local_plugins/review_session/docs/adr/0001-viewer-driven-sessions.md), with commands and limitations in the [plugin README](../src/vim/local_plugins/review_session/README.md). Research evidence below is retained as historical context, not a requirement to enroll comparisons.

- A session is a disposable workspace collecting activity across normal viewer navigation. It has no fixed base/head and requires no comparison setup. Loading/navigating codediff or Fugitive performs no session writes, snapshot persistence or enrollment. Only thread creation, explicit reviewed actions and other deliberate discussion/publication edits persist activity.
- Explicit actions capture the actual file pair shown: repository, old/new paths, exact committed or index-stage versions, saved working-tree content, modes and selected side/range. Immutable original snapshots remain inspectable without Git objects. Unsaved source edits must be saved before anchoring; ambiguous or three-way diffs fail with an actionable error.
- Reviewed means this exact content/metadata pair was marked. Otherwise show “another revision reviewed” when any different pair of that file was reviewed in the session, or pending. This hint implies neither ordering nor partial coverage. Reviewed history exposes which captured pairs were marked. Identical pairs retain their mark across viewer contexts.
- Bulk actions target the viewer's actual change list, including collapsed directories and distinct staged/unstaged pairs at one path. Fugitive status bulk is restricted to the current staged or unstaged section; range comments require an open diff. Fugitive uses HEAD:index for staged status and index:worktree for unstaged status.
- Thread selection defaults to the current view, with easy session-wide access. Choosing a thread from another pair/commit opens its original context in a configurable preferred viewer, default codediff, with immutable snapshot fallback. Thread identity is independent of viewers; ordinary Markdown composition/editing and fzf-lua/native pickers remain supported.
- Session selection is tab-local. New viewer tabs inherit the originating tab's selected session without storage writes; existing tabs retain their selection. Only the active context paints source annotations, including shared source buffers, and switches synchronously clear/repaint cached annotations before asynchronous queries.
- Human-created threads start human-only until explicitly shared; agent-created threads start shared. Human-only is a context filter, not secrecy. Exact message-revision acknowledgements, edit/revert notifications, independent resolution/handling/publication state, deliberate new input on outdated threads, safe concurrent writes and session-level review coverage remain required.
- Publish only an explicitly selected frozen draft, validate the destination PR and applicable source coordinates, and retain remote receipts. Original intermediate anchors are never silently mapped to the current PR. Explicit reanchor or publication as a PR-wide summary supplies the fallback when an inline location is incompatible; reanchoring preserves the original anchor and snapshots. Deleting a session does not undo source changes or remote comments.
- Python owns standalone CLI/session domain rules; Lua owns Neovim UI and optional replaceable codediff/Fugitive adapters. Batch asynchronous read-only queries and cache decorations, with no CLI process per file or redraw. The new plugin supersedes review_tracker without source REVIEWED markers or stripping existing text.

## Historical research and design evidence

The following investigation preceded the viewer-driven decision. Its tool findings remain useful evidence; descriptions of the former fixed-comparison design are superseded by the accepted behavior above.

## Assessment

- The workflow is technically sound: make the durable unit a discussion attached to a specific code version, and let Neovim and independent agents read/write that record. This can remove copying between code, notes, chat, and publication drafts.
- The same need appears in several independently developed projects. That supports treating it as a recurring tooling problem; it does not establish how prevalent it is.
- The primary automation requirement is a deterministic queue of shared threads with new human input requiring agent attention. Context reduction is optional: the agent may already know the thread or retrieve discussion/source as needed. Session rollback is less costly when decisions remain in the durable record.
- A new tool and CLI are acceptable if they make iteration easier. Prefer an existing adequate data format where one exists; otherwise define a documented model usable by independent frontends. Native Markdown composition, independently running agents, historical anchors, outdated filtering, and human-only notes remain requirements.
- Conventions on an existing backend are acceptable even when some requested fields are not native. Canonical human-editable Markdown is optional; viewing discussions as ordinary Markdown and navigating them in Neovim is required. The two logical roles are human and agent, independent of which agent session responds.
- Human-created threads default to human-only until shared. Agents may start shared threads during review or walkthrough; these await human attention. Untouched outdated threads can be excluded from the agent queue, but deliberate new human input on them still requests attention.
- **Session lifetime:** A review session owns its folder/file and can cover a PR stack. It survives editor/agent restarts while present and can be deleted when finished. Permanent repository-wide history is unnecessary. Distinct session paths should permit independent sessions in the same source repository without a repository-global active-session variable.
- **Editing and visibility:** Whole-thread Markdown viewing plus separate normal Markdown message-editing buffers is acceptable. Withdrawal history has no special retention requirement; use the simplest behavior. Human-only visibility is a soft context filter, not a filesystem secrecy boundary.
- **Source snapshots and refresh:** Retain annotated file versions within the session. Refresh committed comparisons explicitly; let working-tree comparisons follow edits live while retaining original annotation context.
- **Current direction:** Prefer session-owned storage and a narrow review CLI over adapting a repository-wide tracker by default. git-bug remains an optional storage reuse candidate; it could be housed in a disposable Git repository inside a session folder, with explicit references to the source repository. That is an architectural possibility, not a tested configuration. Append-only history inside such a session would not require retaining the session forever.
- The difficult parts are immutable anchors, safe concurrent writes, visibility, and publication semantics. The annotation popup and picker are comparatively small concerns.

## review.nvim: codediff annotations and outgoing export

Inspected main at `0a379fae01709645956005f76c4650b7740931a3`. [Project README](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/README.md).

- **Existing UX:** Direct codediff.nvim integration; old/new-side line and range annotations; file comments; four comment types; editable Markdown input; comments on ordinary source buffers. Extmarks track ordinary-buffer notes through live edits and persist updated line numbers on save. [Comment schema](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/store.lua), [popup](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/popup.lua).
- **History viewing:** Can open a single commit, arbitrary revision range, or branch comparison without checking out another branch. Current-branch comparison includes working-tree changes. This is useful for reviewing history but does not establish historical comment identity. [Opening reviews](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/init.lua#L187).
- **Persistence:** One JSON store per repository in Neovim's data directory, shared across branches. Default close exports, archives, then clears comments; `export.clear_on_close=false` retains them. Archives expire after 30 days, active comments do not. [Storage behavior](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/README.md#how-comments-are-stored).
- **Agent interface:** Clipboard/Markdown export, a generic `on_export(markdown, comments)` callback, and sidekick.nvim delivery. No built-in inbound replies, threads, resolved-thread state, message processing checkpoint, private-note channel, or GitHub publication found. Per-file reviewed marks are coverage tracking, not discussion resolution. [Export implementation](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/export.lua), [reviewed marks](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/reviewed.lua).
- **Anchor gap:** Stored fields include path, range, old/new side, text, type, timestamp, and checked-out branch. They omit base/head SHA and PR identity. Two historical comparisons can therefore share an indistinguishable comment location. The captured branch may differ from the branch being viewed. [Store fields and creation](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/store.lua#L5).
- **External-write gap:** Comments load once into memory; later updates rewrite the cached whole JSON store using a plain file write. Direct agent edits could be ignored or overwritten. This is not an external-write protocol. [Load-once behavior](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/store.lua#L38), [JSON writes](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/storage.lua#L123).
- **Picker fit:** Uses `vim.ui.select`. This dotfiles repository already calls `fzf-lua.register_ui_select()`, so the existing adapter should cover the comment picker, subject to runtime verification. [Comment picker](https://github.com/georgeguimaraes/review.nvim/blob/0a379fae01709645956005f76c4650b7740931a3/lua/review/comments.lua#L205), [local adapter](../src/config/nvim/config/plugin/find/fzf.lua#L180).

**Fit:** Good existing codediff annotation UX. Turning it into a durable threaded agent conversation tool would require substantive changes to its model and persistence.

## code-review.nvim: the closest small Neovim experiment

Inspected main at `ed91462e20bd08c3be71efb11a4a7d00459f0b47`. [Project README](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/README.md).

- **Existing UX:** Thread creation and replies, resolve/reopen, Markdown input, editable preview, signs/virtual text, fzf-lua/Telescope/quickfix pickers. Telescope takes precedence when both pickers are available; the fzf-lua functions can also be called directly. [Thread state API](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/state.lua), [thread picker](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/list.lua#L479), [Markdown buffers](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/ui.lua).
- **Persistence:** Default storage is session memory. File backend opts into `.code-review/` or a configured directory. Despite README wording about one file per comment, current source stores each whole linear thread in its root file and rewrites it on reply. Frontmatter identifies path/range/author/time/thread, followed by captured code context and Markdown message sections. [File reply writes](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/storage/file.lua#L337), [thread format](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/storage/file.lua#L719).
- **Independent agents:** Agents can edit the files directly. File backend reloads on `BufEnter`, `BufWritePost`, and `CursorHold`, so external edits can appear without restarting Neovim. This is event-triggered refresh, not a continuously pushed stream. [Reload autocmds](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/init.lua#L136).
- **Pending-thread queue:** `comment.status_management=true` enables `action-required_`, `waiting-review_`, and `resolved_` filename prefixes. Latest author matching configurable `claude_code_author` means waiting for human review; other authors mean agent action required. File-backend resolve/reopen requires this option. Bundled shell scripts monitor/rename these files, but are not a full annotation CLI. [Status calculation](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/storage/file.lua#L48), [resolve](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/storage/file.lua#L616), [monitor example](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/.claude/scripts/review-loop-monitor.sh).
- **Anchor gap:** Generic current-buffer path and line range, plus captured source text. No old/new side, comparison SHAs, PR identity, snapshot identity, or dedicated codediff/diffview adapter. README's diffview companionship is not version-aware anchoring. No explicit review-wide/file-wide target kind or private channel found. [Selection capture](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/utils.lua#L83), [schema](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/thread.lua#L9).
- **Storage limits:** Whole-thread writes have no locking or compare-and-swap. Unknown frontmatter is not retained through parsing/rewriting, so adding SHAs manually is insufficient. Reloaded message IDs derive from filename and position. The parser treats every `### ` line as a new message and discards `---` separators, including such text within message bodies. Unrestricted Markdown and stable incremental processing need a stronger format. [Parser](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/storage/file.lua#L115), [write helper](https://github.com/choplin/code-review.nvim/blob/ed91462e20bd08c3be71efb11a4a7d00459f0b47/lua/code-review/utils.lua#L172).
- **Publication gap:** No GitHub comment import/publish or per-consumer message acknowledgement found. Filename status selects pending threads but cannot identify exactly which message revisions an agent handled.

**Fit:** Try file backend, status management, a configured agent author, and explicit turn-taking to evaluate the core interaction. Historical/stacked PR review and reliable publishing remain real implementation work.

## Hunk: threaded agent replies already exist, durability does not

Inspected main at `78101bf078cff3363539b79abf8464a6f551f19a`; latest published release observed was `v0.24.1` (2026-10-25). Core `--reply-to` is documented in the release, not only on main. [Released agent skill](https://github.com/modem-dev/hunk/blob/v0.24.1/packages/hunk/skills/hunk-review/SKILL.md).

- **Existing conversation:** Human adds a note on a diff line; external agent inspects notes and runs `hunk session comment add --reply-to <note-id>`. Replies inherit the parent's source anchor and render under it. The agent can filter notes by type/file and submit a validated JSON batch. [Comments guide](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/website/src/content/docs/docs/agents/comments-and-annotations.md), [live note model](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk/src/core/review/types.ts).
- **History viewing:** Commit, arbitrary ref/range, log selection, GitHub PR/commit/compare input. These can review code different from the checkout. [History workflows](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/website/src/content/docs/docs/workflows/working-trees-and-commits.md).
- **Lifecycle blocker:** Live human and agent notes are in memory and closing the Hunk window discards them. Its local daemon lets agents and the TUI communicate, and Neovim can restart independently, but this is not a durable conversation notebook. [Documented lifetime](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/website/src/content/docs/docs/agents/comments-and-annotations.md), [store initialization](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk/src/core/review/store.ts).
- **Two different annotation models:** Static `--agent-context` sidecars can reload under `--watch`; live human/agent threads use a richer model. Sidecar fields include file path, old/new ranges, rationale, tags, author, confidence, and timestamp. They omit review SHAs, thread parents, private visibility, resolved state, and read cursor; normalization drops extra fields. The sidecar is not a serialization of live threads. [Sidecar guide](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/website/src/content/docs/docs/agents/agent-context-and-stml.md), [parser](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk/src/core/changeset/sidecar.ts).
- **Live anchor handling:** Source/content identities and active/stale/orphaned reconciliation exist. Its `resolution` field means anchor validity, not user-resolved discussion. The live protocol supports generation/revision concurrency checks, but neither supplies persistent per-commit review history. [Identity](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk/src/core/review/identity.ts), [state](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk/src/core/review/state.ts), [concurrency protocol](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk/src/session/reviewProtocol.ts).
- **Context selection:** `session review --json` omits patches by default; `--include-patch` and `--include-notes` opt in. Comment listing filters by author category/file. No built-in new-since/per-agent acknowledgement cursor found; live `stateRevision` counts arbitrary state mutations. [Agent skill](https://github.com/modem-dev/hunk/blob/v0.24.1/packages/hunk/skills/hunk-review/SKILL.md).
- **Editing and privacy gaps:** Note composition is an OpenTUI textarea, not a native Neovim buffer; no external-editor composer found. Human notes are agent-readable and mutable, not private. No first-class review-wide/file-wide thread roots or fzf-lua integration found. [Composer](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk/src/ui/components/panes/AgentInlineNote.tsx#L661), [note model](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk/src/core/review/types.ts).
- **GitHub gap:** Bundled GitHub integration reads diffs/metadata; it does not import/synchronize discussion threads or publish reviews. A snapshot-export extension preserves saved live notes but provides no import/resume path. Extension APIs are experimental. [GitHub implementation](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/packages/hunk-gh/src/github.ts), [snapshot example](https://github.com/modem-dev/hunk/blob/78101bf078cff3363539b79abf8464a6f551f19a/examples/extensions/review-snapshot-export/README.md).

**Fit:** Useful for testing whether threaded inline agent discussion feels effective. Do not adopt its current sidecar as the canonical durable review record.

## Earlier annotation tools and a reusable review format

- **CodeReviewer.vim:** Vim.org records initial release on 2004-07-21. Its workflow captures filename, line, reviewer and defect type into a separate review file and uses quickfix for navigation. Code annotations independent of source edits predate coding agents by decades; the format is a flat review list rather than a threaded revision-aware record. [Original plugin page](https://www.vim.org/scripts/script.php?script_id=1041).
- **vim-bookmarks, 2014:** Persistent personal line annotations, including preparing code reviews, without modifying source. Saved data is generated Vimscript, not an interoperable structured thread format. No commit-aware discussion model found. [README](https://github.com/MattesGroeger/vim-bookmarks/blob/9cc5fa7ecc23b052bd524d07c85356c64b92aeef/README.md), [serialization](https://github.com/MattesGroeger/vim-bookmarks/blob/9cc5fa7ecc23b052bd524d07c85356c64b92aeef/autoload/bm.vim#L163).
- **Ash + Ashium, 2015:** Existing pre-agent interaction precedent for editable review files containing line/file/review comments and threaded replies. Ash supplies the Stash review CLI; Ashium integrates Vim and refreshes remote comments while reviewing. Remote Stash integration and old runtime assumptions make this a design reference, not a verified local backend. [Ash review-file workflow](https://github.com/seletskiy/ash/blob/9b2351122de4f6b5520b6753b5dadba2edb313f0/README.md#reviewing), [Vim frontend](https://github.com/seletskiy/ashium/blob/3d8281f612bdfab3d5e7457a706c9892d19d688d/README.md).
- **Git Appraise:** A distributed review CLI whose repository dates to 2015. Its documented JSON-in-Git-notes format has comment authors/timestamps, parent hashes for replies, original hashes for edits, commit/path/range locations, and resolution. Omitted path/range represent commit/file scope. Review requests contain a comparison base and a ref tracking the review revision. JSON output and reply creation are already CLI operations. This is a stronger existing format candidate than a flat annotation sidecar. Inspected `be4751005fb49ddfc7b7f01259d1d4906aa288bf`; the repository's last push was 2023-08-12. [README and storage format](https://github.com/google/git-appraise/blob/be4751005fb49ddfc7b7f01259d1d4906aa288bf/README.md), [comment schema](https://github.com/google/git-appraise/blob/be4751005fb49ddfc7b7f01259d1d4906aa288bf/schema/comment.json), [request schema](https://github.com/google/git-appraise/blob/be4751005fb49ddfc7b7f01259d1d4906aa288bf/schema/request.json), [reply CLI](https://github.com/google/git-appraise/blob/be4751005fb49ddfc7b7f01259d1d4906aa288bf/commands/comment.go), [thread reconstruction and resolution](https://github.com/google/git-appraise/blob/be4751005fb49ddfc7b7f01259d1d4906aa288bf/review/review.go).
  - **Remaining gaps:** Inspected schemas have no agent-attention acknowledgement, human-only visibility, selected publication draft, or working-tree snapshot type. Source anchors identify commits, not an explicit old/new comparison side. Adopting the CLI also adopts Git-notes storage and writes review objects into the repository. No tool was installed or run; runtime compatibility, editor integrations and concurrent operation are unverified.
  - **GitHub caveat:** The linked GitHub mirror documents importing PR metadata into Appraise, not the desired approved-draft publisher. Do not assume bidirectional synchronization from the existence of that integration. [Mirror README](https://github.com/google/git-pull-request-mirror).
  - **Assessment:** Evaluate this format/backend before deciding that a new one is necessary. Its explicit parent/edit/revision relationships are useful precedent even if working-tree, privacy and attention requirements justify a smaller dedicated implementation. Do not add mandatory Git-notes storage merely to imitate its data model.
- **Newer annotation reference:** Punchlist.nvim (2026) keeps annotations outside source and explicitly represents stale/orphaned content anchors, external reload and manual reanchoring. ## Backend investigation with conventions accepted

These findings were added 2026-11-10. Missing native review fields are not treated as blockers when a small documented convention can supply them. No backend was installed or executed.

### git-bug: a viable persistence layer

Inspected trunk `75c565b6c8da2cf07b6fb9d7808924850d9067a9`; latest release observed was v0.12.0 (2026-11-07). Operations live in Git objects under dedicated refs. Stable bug and comment IDs, append-only edit history, labels, open/closed status, JSON reads, and concurrency handling supply useful infrastructure. Edits preserve original comment identity. Expected-old-ref checks and cache repair/retry were verified in the release too. [Release](https://github.com/git-bug/git-bug/releases/tag/v0.12.0), [data model](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/doc/design/data-model.md), [comment identity](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/entities/bug/comment.go), [released concurrency recovery](https://github.com/git-bug/git-bug/blob/v0.12.0/cache/cached.go#L180).

- **Proposed mapping:** One bug represents one discussion, with comments as messages and open/closed as thread resolution. A versioned structured block in the opening Markdown holds review identity and original source anchor. Labels index review membership, visibility and outdated state. A message convention identifies the human/agent role where native identities do not distinguish it, and a reply identifies the message revision it handles. These are application conventions, not native git-bug semantics.
- **Deterministic queue:** Derive pending work from unacknowledged human message revisions. A label such as needs-agent can be an index, but must not clear a newer human message when an older agent reply arrives. Plain JSON comments expose ID/author/current body, not edit-operation identity. Hashing the current body detects different text but misses A-to-B-to-A edits ending in previously acknowledged text. Exact edit notifications require AddComment/EditComment operation IDs. GraphQL exposes these through a local server; a small Go CLI adapter can instead read Bug.Operations() without a daemon or backend fork. [CLI JSON](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/commands/cmdjson/bug.go), [operation fields](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/api/graphql/schema/bug_operations.graphql), [Go operation API](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/entities/bug/bug.go#L142).
- **Metadata alternative:** The Go model supports per-operation metadata, but stock CLI and GraphQL mutations do not expose arbitrary metadata writes. Body conventions avoid requiring a backend fork. If using the Go API, metadata is first-write-wins per target/key, so acknowledgements belong on new operations rather than overwriting a cursor property. [Cache APIs](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/cache/bug_cache.go), [metadata semantics](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/entity/dag/op_set_metadata.go).
- **Domain work remains:** Source anchor validation, working-tree snapshots, reanchoring, human-only filtering, Markdown rendering, selected publication draft and PR destination mapping remain in the review adapter. This is smaller in scope than replacing persistence, identities, edits and merge handling.
- **Keep the deliberation store unbridged:** The GitHub bridge handles Issues, not PR inline reviews, and does not recognize an application-private label. Stock push has no per-label selection. A separate explicit-draft publisher is still required. [Bridge exporter](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/bridge/github/export.go), [feature matrix](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/doc/feature-matrix.md).
- **Withdrawal is an application operation:** No comment-delete subcommand or GraphQL mutation was found. A tombstone/retraction convention can hide an exchange while retaining recoverable history. Concurrent edits of the same comment still require UI conflict handling; preserving unrelated appended comments does not merge their prose automatically. [Comment commands](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/commands/bug/bug_comment.go), [comment edit operation](https://github.com/git-bug/git-bug/blob/75c565b6c8da2cf07b6fb9d7808924850d9067a9/entities/bug/op_edit_comment.go).

**Assessment:** git-bug can supply persistence and edit/concurrency infrastructure beneath review conventions. For the clarified disposable-session lifecycle, its repository/tracker machinery must justify its cost compared with a session-owned file/database. No runtime evaluation or isolated-session configuration was performed.

### prr: an outgoing review document

Inspected `danobi/prr` master `8de3b12abe9c763874056bd818be1c982065a0b2` (manifest 0.21.0, repository pushed 2026-10-24). `get` downloads a PR, `edit` uses the real editor, and `submit` posts a GitHub review. No checkout is required. A `.prr` file contains a quoted frozen diff plus unquoted outgoing comments. A sibling metadata file preserves original diff, downloaded head SHA and submission time. It supports review/file/line/range comments and checks that quoted diff text still matches its original. [Format](https://github.com/danobi/prr/blob/8de3b12abe9c763874056bd818be1c982065a0b2/book/src/review.md), [metadata and validation](https://github.com/danobi/prr/blob/8de3b12abe9c763874056bd818be1c982065a0b2/src/review.rs), [Vim support](https://github.com/danobi/prr/blob/8de3b12abe9c763874056bd818be1c982065a0b2/book/src/vim.md).

- It has no local message identities, authors/roles, reply tree, visibility, per-message acknowledgement, remote-thread synchronization or selected historical-comparison CLI. Writing human/agent dialogue into a `.prr` file would make all of it outgoing comment text. It is a publication document, not a discussion ledger. [Parser types](https://github.com/danobi/prr/blob/8de3b12abe9c763874056bd818be1c982065a0b2/src/parser.rs), [CLI](https://github.com/danobi/prr/blob/8de3b12abe9c763874056bd818be1c982065a0b2/src/cli.rs).
- Automation limits matter: `submit --debug` prints JSON and then actually publishes. Repeated submission is not prevented, remote IDs are not retained, and file comments are posted after the main review was already marked submitted. A partial failure is not safe to retry wholesale. Refresh replaces rather than ports comments. [Submission control flow](https://github.com/danobi/prr/blob/8de3b12abe9c763874056bd818be1c982065a0b2/src/prr.rs#L311).
- **Assessment:** Possible optional final review editor with deliberate one-time submission, but not a candidate for the canonical conversation store. A small publisher over gh may be simpler for explicit drafts, previews and retry receipts than adapting positional `.prr` syntax.

## ACP and GitHub boundaries

- **ACP:** Session creation/loading, streamed updates, file operations, and tool locations provide editor-agent integration. Inspected `ToolCallLocation` is a path plus optional line, not a first-class historical review thread with SHAs, side/range, resolution, or unread state. Extensions could carry that model, but ACP does not supply it. Session replay also differs from retaining an independent process after editor exit. [Tool calls](https://agentclientprotocol.com/protocol/v1/tool-calls), [session setup](https://agentclientprotocol.com/protocol/v1/session-setup), [schema snapshot `5731ad9591f447c9034ae78f392533019b08a187`](https://github.com/agentclientprotocol/agent-client-protocol/blob/5731ad9591f447c9034ae78f392533019b08a187/schema/v1/schema.json).
- **GitHub target mapping:** Line/range comments use `commit_id`, `path`, `side`, `line`, and optional `start_line/start_side`; file comments use `subject_type:file`. Replies use the review-comment ID. Historical SHAs are supported but later edits can make comments outdated. PR review comments target the PR diff, not arbitrary local comparisons. [Review-comment API](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request).
- **Review-wide comments:** Use an overall review body or a regular PR issue comment. Pending reviews allow preparation before submission. A review batch has one commit target, so a ledger spanning PRs/commits needs grouping or explicit mapping. [Review API](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request), [comment types](https://docs.github.com/en/rest/guides/working-with-comments).
- **Publisher implications, engineering judgment:** Store original comparison identity separately from publication destination. Validate PR, publishing SHA, path, side, and range; preview selected drafts; preserve remote IDs/receipts for retries. A lower-stack finding need not belong to the checked-out upper PR. If a historical anchor no longer maps, retain it and explicitly reanchor or publish a linked summary rather than silently choosing a current line.


## Deterministic agent attention and session independence

These are engineering inferences, not measured token savings.

- Current unstaged comments make comments discoverable and let the agent inspect their diff. They do not provide message identity, reply state, history targeting, privacy, or persistence independent of source edits. Token use depends on how much code/history is read, not whether the comment was found through `git diff`.
- A pending-thread query should identify stable threads and the new or edited human messages requiring attention, without searching staged/unstaged source for comment-like text. Thread history and source can be fetched separately as needed; an export need not predict how much context the agent already has.
- A fresh agent cannot reason reliably from only the latest reply when it depends on prior conclusions. Durable storage enables reconstruction, not omission of required context. An existing long chat also retains unrelated topics unless a fresh/focused invocation or compaction removes them.
- A latest-human-author queue is enough for a basic turn-taking experiment. It needs explicit revision acknowledgements when users edit earlier messages, agents crash/retry, or multiple agents consume the queue. Reading a message is not successfully handling it.
- Focused invocations can reduce unrelated context, but reload repository guidance and source; summaries can lose necessary facts and caching changes cost. Compare total input/output, latency, repeated reading, and human bookkeeping on representative PRs before claiming efficiency.
- Editor and agent lifetimes should be consumers of the durable review record. Restarting/forking either can then recover thread context and decisions without reconstructing the conversation from chat history.

## Architecture boundaries worth preserving

This is a proposed direction, not an implementation commitment.

- **Keep the record independent:** Persist review identity, threads, messages, anchors, state, and selected publication drafts in an explicitly selected review session, independently of agent sessions and open editor buffers. CLI and Neovim should operate on the same data. Deleting the review session discards its local record; it does not undo source changes or published GitHub comments. Avoid writing another agent harness.
- **Model three scopes:** Review-wide, file-wide, and source-range threads. Associate each with a review target; do not force global notes onto an arbitrary line.
- **Freeze original anchors:** Repository plus exact comparison base/head, side, old/new path where needed, and range. Working-tree text needs captured snapshot/content identity because HEAD alone does not identify it. Keep the original location and derive any newer projection separately; mark stale or ambiguous mapping visibly. Unmapped historical threads remain available as outdated and can be filtered by humans and agents.
- **Keep thread state distinct:** Discussion resolved, agent processed, and publishable are separate decisions. Resolving an internal question can produce a valid author-facing finding; an open exploration may be unsuitable for publication.
- **Select the publication draft:** Use an explicit message/draft selection rather than the last reply. Otherwise a final grammar-check acknowledgement could become the published comment. Polishing can remain in the same thread without changing this selection accidentally.
- **Write safely:** A narrow CLI can enforce validation and serialized or revision-checked writes. Direct file editing is reasonable for turn-taking, provided the editor reloads and format preserves metadata. Atomic replacement alone prevents partial files, not lost updates between writers.
- **Keep private notes anchored:** Human-created threads start human-only and become shared through an explicit action; agent-created threads are shared and await the human. GitHub publication is a separate selection. Filter human-only content out of normal agent commands; a filesystem secrecy boundary is not required.
- **Infer requested action:** Agents may answer, investigate, disagree, propose a fix, or change source according to the comment's intent. Question/change-request labels may be useful hints, but are not mandatory gates. Personal instructions still require challenging wrong/debatable comments rather than blindly obeying them.

## Fit with the existing clj-code-review skill

- Its required review target/base, intended behavior, guidance record, and coverage checklist belong at review scope. Keep that evidence once, rather than copying the whole checklist into every thread. [Local skill](../src/nixos/modules/ai/codex/skills/clj-code-review/SKILL.md).
- Each concrete finding or independent discussion can become its own anchored thread with evidence, consequence, and uncertainty. Replies can refine or reject it without losing adjacent findings in a single chat timeline.
- The review record can preserve both findings and completed/inapplicable/unverified coverage. Thread resolution does not demonstrate that an unrecorded planned check was completed.
- Existing subagent review delegation can remain unchanged; the result destination and follow-up loop would change. Independent agents use the same thread/anchor contract rather than owning the only copy of the review.

## Smallest useful evaluation

- Evaluate the session contract before selecting a backend: one session can group a stack's comparisons and threads, and editor/agent commands explicitly select it.
- Verify that pending work survives restarting both consumers, that a reply cannot acknowledge newer human input accidentally, and that two sessions in the same repository remain independent.
- Use navigable Markdown thread views and ordinary per-message editing buffers. Reuse codediff for code/diff presentation rather than creating another diff renderer.
- Keep annotated file versions, publication receipts and any other local session state within its deletion boundary. Verify that original annotation context remains inspectable if Git no longer provides the referenced revision.
- Existing tools remain useful references or optional adapters. Historical anchors, privacy, and publication cannot be inferred from a tool merely displaying a historical diff.

Unverified: interactive UX, installation compatibility, performance, end-to-end GitHub publication, and token/cost improvements. Source branches and release features can differ; exact inspected snapshots are recorded above where available.
